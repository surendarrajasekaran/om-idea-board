# Platform, reliability, cost and security review

Reviewed October 31, 2026 against the current local source. The assignment's two public cloud deployments remain pending. These changes are not evidence of a successful Terraform apply or a live-cluster recovery exercise.

## Findings and implemented controls

| Finding | Impact | Implemented change |
| --- | --- | --- |
| Cloud adapters combined network, cluster and database resources, with fixed address/capacity settings | Difficult to reuse components or right-size an environment | Six provider-free modules; typed configuration for CIDRs, AZs, nodes, classes/tiers, storage, backups, labels and retention; preserved resource address history with moved blocks |
| Custom Terraform names did not isolate remote state/application names | A second application could target the original stack/state | Validated `--name` through state initialization, Terraform inputs/outputs, releases, namespace, Services and Secrets |
| Invalid image flags/reused profiles could be discovered after apply | Chargeable infrastructure could be created for an invalid invocation | Validate file existence, target/profile policy, image references, image-mode flags, registry identity and production HTTPS before cloud-changing commands |
| API used the database administrator login | An application compromise could administer the database | Distinct runtime password and migration URI; only init container gets migration credentials; runtime gets SELECT/INSERT and sequence usage; no role memberships, database creation, role creation, replication, superuser or schema DDL privileges |
| Database TLS required encryption but did not verify the peer | A substituted server certificate could go undetected | RDS `verify-full` plus official CA bundle; Cloud SQL `verify-ca` plus its unique per-instance CA; read-only CA mounts and CA/credential rollout fingerprints |
| Cluster APIs were public by default | Public control-plane exposure depended solely on allowlists | Private endpoints by default on both clouds; public access requires explicit opt-in and `/24` or narrower trusted CIDRs; GKE enforces private endpoint authorized networks |
| EKS node metadata was reachable with the upstream hop-limit default | Pods could inherit worker-node IAM credentials | IMDSv2 required, hop limit 1, no metadata tags; app pods have no IAM needs and no token mounts |
| GKE relied on the project's default node identity | Default account might have excess permissions | Dedicated, uniquely named node service account with `roles/container.defaultNodeServiceAccount`; application workloads receive no cloud roles |
| No workload network isolation or namespace admission policy | A compromised frontend could move laterally or access cloud metadata | Restricted Pod Security, RuntimeDefault seccomp, read-only roots, bounded writable Nginx directories; default-deny ingress/egress; only frontend→API, API→private DB and DNS paths permitted; EKS CNI policy enforcement enabled |
| Default node egress allowed every protocol/port to the Internet | Excessive network access after node compromise | Disable upstream egress-all; explicit HTTPS, VPC DNS, node-local cluster traffic and private database rules; one scoped scanner exception for public HTTPS |
| Public production access had no TLS enforcement | Ideas could cross the public network in plaintext | Production CLI requires an existing TLS Secret and certificate DNS hostname; frontend terminates TLS 1.2/1.3 on 8443 behind Service 443; health/smoke clients retain certificate verification |
| Worker/database/storage/log settings were fixed or unbounded | Idle staging cost and uncontrolled growth | One AWS worker in staging, >=2 on-demand workers in production; configurable pool and DB size; gp3 storage, 100 GiB growth cap, bounded AWS log retention, sampled GCP flow logs, bounded namespace resources |
| EKS 1.33 default had passed standard support | Extended-support charges and aging Kubernetes baseline | Default 1.35, STANDARD support policy, documented proactive upgrade responsibility |
| Upgrades could concentrate replicas on one worker | Reduced protection against worker loss | Production hostname spread plus disruption budgets; staging accepts single-worker availability tradeoff |
| Database operations had no connection/query/lock bounds | Slow connections/queries could consume worker threads and DB connections | Five-second connection/pool limits; API query/lock/idle-transaction deadlines; longer, bounded migration deadlines; recycled pooled connections |
| Mutable Action/base image tags and old Trivy Action reference | Supply-chain substitutions could execute with CI credentials | Verified commit SHAs for all external Actions; base/PostgreSQL image index digests; removed Trivy Action wrapper; shared 0.76.1 scanner container pinned by digest, no Docker socket, unprivileged/read-only/capability-free with disposable disk cache and resource bounds |
| Infrastructure/release workflows had different concurrency locks | Provisioning and rollout could overlap for one target | Shared platform/cloud/environment lock, unique Terraform working directories and job timeouts |
| Persistent checkout/Docker credentials and broad secret exposure | Credentials could survive on a trusted runner or reach unrelated steps | Checkout persistence disabled; cloud auth after dependency/artifact preparation; GHCR/live-AI secrets scoped to their steps; CLI Docker config isolated and removed; saved plans removed; provider lock file read-only |
| Security could regress without a CI gate | Hardening would remain a one-time exercise | Both-cloud IaC scans in CI; provider-mocked Terraform tests; invalid-input, namespace/policy, HTTPS render, runtime-role and chart-integrity tests; weekly Dependabot configuration |

## Operational decisions and residual risks

- **No cloud deployment or live rollback has been performed.** Plan with real identities and quotas, exercise actual connectivity/policy enforcement/CA handling on EKS and GKE, run public smoke/persistence checks, and deliberately fail a release on each cluster. Mocked Terraform/Helm tests cannot establish those results.
- **Worker HTTPS exception:** `.trivyignore.yaml` scopes AWS-0104 to the upstream node security-group file until January 31, 2027. Effective public node egress is TCP/443 for dynamic GHCR/AWS endpoints, not all protocols. Application egress is separately denied. A registry mirror plus egress proxy/private endpoints can remove this exception; static GHCR IP allowlists would be fragile. Review the exception before expiry.
- **Private access is a prerequisite:** the self-hosted runner must have private network routing and the correct source CIDR, not merely OIDC credentials. A workstation without VPN/private routing cannot use the private default. Public endpoint opt-in is an explicit security exception, not part of the clean default scan result.
- **TLS requires owned DNS/PKI:** deployment consumes an existing certificate Secret and DNS name; it does not issue certificates or own DNS. Configure renewal/expiry alerts and the DNS record for the printed load-balancer address. Cloud SQL direct private-IP TLS validates the unique instance CA rather than a DNS hostname. Use Cloud SQL Auth Proxy/Connector if a different topology or full managed identity verification is required.
- **Rollback preserves security boundaries:** namespace quotas and network policies are applied outside Helm, so reverting to an older application revision cannot remove them. Database data, roles, CA/credential Secrets and infrastructure are not rolled back automatically. Coordinate credential/CA rotation with overlapping trust; an application rollback cannot repair a broken database credential change.
- **No product authentication/moderation:** the assignment remains an anonymous board. Rate limiting is basic and load-balancer client-IP trust needs live verification. Anyone who can reach the public app can submit ideas. Do not treat it as an authenticated company system. Pagination, retention and application-level abuse controls are still needed for high traffic.
- **Bootstrap IAM/state remain trust roots:** OIDC trust, least-privilege provisioning/deployment roles, RBAC, encrypted/versioned state buckets, access auditing, billing budgets and short-lived runner isolation need account configuration. Terraform state contains passwords. No broad account policies, cloud budgets, runner fleet or existing project resources were created/changed in this pass.
- **Encryption keys:** databases use provider-managed encryption at rest; EKS uses its module-managed KMS encryption. Organization-specific CMEK, key ownership and rotation policies remain an integration choice. GCP Logging retention is project-level and is not silently changed by a reusable application module.
- **Logs are not an SLO system:** flow logs, EKS audit/control-plane logs, RDS logs and app metrics exist, but alert routes, scrape infrastructure, retention ownership, SLO dashboards, backup restore drills and on-call escalation are not configured. Do not count backups as tested restores.
- **Capacity is a starting point:** one staging node saves idle capacity but has downtime during node loss/maintenance. Production baseline is >=2 on-demand workers; node-group bounds do not install an autoscaler. GCP app resource proposals obey the CPU/memory ratio to avoid unexpected request inflation. Measure load before increasing or reducing these settings.
- **Reproducibility needs updates:** digest/commit pins prevent silent tag movement but become stale. Review Dependabot updates, refresh the explicit scanner digest after checking upstream advisories, and keep Kubernetes/node/add-on/client versions supported. Runtime OS upgrades and vulnerability databases intentionally change over time; release scans are repeated.
